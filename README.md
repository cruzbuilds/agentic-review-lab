# agentic-review-lab

How much review structure does AI-written code actually need before a person can trust it?

AI coding systems generate working software now. Generating it and being able to vouch for it are
different problems, and the second one is the one that stops teams from using the first. This is the
front door for a set of repositories that work on that second problem with practical engineering
experiments: build a review architecture, test its assumptions on real code, keep the evidence,
change the architecture when the evidence says to.

**Where the canonical record is.** As of 2026-09-19 the research record lives with the
implementation, in [agentic-review-swarm](https://github.com/cruzbuilds/agentic-review-swarm) under
`docs/research/`: the progression map, the Experiment 001 entry, the V2 record with its frozen
evaluation runs, the proposed V3, and the paper. This repository is the cross-repository front door and
the pre-implementation design history; where a page here and a page there say the same thing, the
swarm repository's is canonical and this one links to it. Experiment 001's raw data stays in its own
repository, as before.

## The progression

### V1: specialist review swarm

[agentic-review-swarm](https://github.com/cruzbuilds/agentic-review-swarm), as tested.

Five reviewers, each with a written charter in plain English saying what it blocks on, what it warns
on, and what it must stay out of: security, tests, infrastructure, documentation, scope. They inspect
the same change independently and in parallel. An orchestrator merges their reports into one
verdict; any single BLOCK is a BLOCK. Every reviewer is proven against seeded cases before it reviews
anything real.

The assumption underneath V1 was that comprehensive review decomposes into independent lanes, and
that a reviewer with a narrow charter and deeper instructions finds more inside its lane than a
general reviewer would. V1 was built on that assumption and then used on real pull requests, where
it caught things a tired human would have missed. What it did not have was a control: nobody had
checked what one general reviewer would have caught on the same code.

V1 is not claimed to be superior to anything. It was the thing under test.

### Experiment 001: Five Critics or One Good Prompt

[Five-Critics-or-One-Good-Prompt](https://github.com/cruzbuilds/Five-Critics-or-One-Good-Prompt).

Rather than assume V1 was better, I tested it. One application, generated by a coding agent from a
single paragraph and frozen at one commit. Three ways of reviewing it, same model, three runs each:
the V1 swarm, one strong generalist prompt that names every domain, and one naive generalist prompt
of twenty-four words with no domain map. Predictions sealed before any run. Every claim from every
run checked against the code. Everything published, including the failures.

What was observed:

- The strong generalist and the specialist swarm tied on total confirmed defects, 38 each.
- The naive generalist found fewer in total, 30, but found every high-value defect in every run.
- Test specialization produced substantially deeper, actionable decomposition: thirteen module-level
  test items with assertions, every run, where each generalist said "no tests" once.
- Specialist review was more structured and more repeatable, and produced the only per-agent record
  of what was checked, which tools ran, and what could not be examined.
- Broad reviewers were stronger at cross-cutting correctness. The most consequential defect in the
  subject, a logic flaw that lets a user falsify the product's core metric, was found by both
  generalists and by no swarm run as a finding.
- Both generalist conditions out-found the security specialist inside the security lane, 11 and 11
  to 7.
- Hard specialist boundaries caused that correctness finding to become unowned: a swarm agent
  noticed it in two runs and the merged report filed it under "Handoffs nobody picked up: no agent in
  the roster owns this."
- The experiment did not support the broad claim that multi-agent review is inherently better than
  one strong model call. Four of five sealed predictions failed.

Limitations, stated plainly: one repository, one model family, one week, one author who built the
system under test and judged the results with published verdicts and no second judge yet. The subject
had no meaningful existing tests, no CI, and almost no infrastructure, so two of the five specialists
were measured on noticing absence rather than reviewing presence, and their tools had nothing to run
against. None of this generalizes to multi-agent systems as a class.

### V2: hybrid review

The architecture hypothesis motivated by Experiment 001: broad reasoning and specialist depth appear
to be complementary rather than alternatives. V1 had only the second.

```
Broad Systems Review
        +
Specialist Reviews
        |
        v
      Arbiter
        |
        v
Final Findings + Assurance Record
```

The broad review reasons about the application as a system: correctness, business invariants,
cross-file behavior, emergent failures, and anything important that no specialist owns. The
specialists do what they demonstrably did well in V1: deep, repeatable inspection in known domains,
with explicit coverage. The arbiter deduplicates, reconciles disagreements, preserves attribution,
retains unowned serious findings as findings with a severity, and produces one verdict and one
assurance record.

The rule that changes from V1: an important finding must never disappear because it does not fit a
lane.

**V2.0 is built and its mechanisms are evaluated. It is not validated against V1.** On its own
evaluations the systems reviewer reconstructed five of five planted interactions and found defects in
three fixtures nobody planted, the arbiter applied its contract seventeen of seventeen times, and the
integrated run showed no regressions in the V1 suite. Whether V2 recovers the cross-cutting findings
V1 lost on a real subject, at what cost, is the question for Experiment 002, which has not been
designed past a paragraph. The full record, including what is not demonstrated, is
[`docs/research/v2-hybrid-review.md`](https://github.com/cruzbuilds/agentic-review-swarm/blob/v2/hierarchical-review-model/docs/research/v2-hybrid-review.md)
in the swarm repository.

## The shape of the work

Build an architecture. Write down what it assumes. Test the assumptions on real code with the
predictions sealed first. Publish the evidence whether or not it flatters the architecture. Change
the architecture when the evidence says to, and keep the decision history so the change can be
traced.

That is the whole method. The most interesting thing Experiment 001 produced was not a number. It
was a different architecture.
